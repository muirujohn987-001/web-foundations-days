# TicketHub — Ticketing System Design

## 1. Requirements

TicketHub is a website where users discover concerts and events, view available seats, reserve seats, make payments, and access purchased tickets.

The system must support 2 million registered users and handle normal daily traffic as well as sudden traffic spikes when popular concerts go on sale.

### 1.1 Functional Requirements

The system must allow users to:

1. Register, log in, and manage their accounts.
2. Browse upcoming concerts and events.
3. Search and filter events by location, date, category, and price.
4. View event details, venue information, and available seats.
5. Temporarily hold available seats before completing payment.
6. Pay for held seats using supported payment methods.
7. Receive booking confirmation and digital tickets after successful payment.
8. View their purchased tickets and order history.
9. Cancel orders and request refunds where permitted by the event's cancellation policy.
10. Allow event organizers and administrators to create events, configure seating, and monitor ticket sales.

### 1.2 Non-Functional Requirements

**Performance and speed**
- Event listings and event details should load quickly.
- Seat availability should update frequently during popular sales.
- The system should handle at least the estimated traffic generated by the popular concert sale.
- Payment processing should not unnecessarily block browsing and other users.

**Correctness and data integrity**
- A seat must never be sold to two different customers.
- An order must not be marked as paid unless payment is confirmed.
- Expired seat holds must become available again.
- The database must maintain consistent relationships between users, events, seats, and orders.

**Fairness**
- Users should enter a virtual waiting room when demand is unusually high.
- Users should be admitted to the purchasing process in a controlled and fair manner.
- The system should prevent automated clients from bypassing the queue or repeatedly reserving seats.
- A successful seat hold should be temporary and have a clear expiration time.

**Availability and reliability**
- The website should remain available when individual application servers fail.
- Failed payment attempts should not result in lost or duplicated orders.
- The system should support backups and recovery.

**Security**
- Users must authenticate before purchasing tickets.
- Users must only access their own orders and tickets.
- Payment information must be handled securely through a trusted payment provider.
- All communication should use HTTPS.

## 2. Traffic and Capacity Estimates

TicketHub has 2 million registered users. However, not all registered users are active at the same time.

### 2.1 Normal Daily Traffic

Given:
- Daily visitors = 50,000.
- Each visitor views 10 pages.
- Tickets sold per day = 5,000.
- Seconds per day = 86,400.

**Daily page views**

50,000 × 10 = 500,000 page views per day.

**Average page views per second**

500,000 ÷ 86,400 ≈ 5.79 page views per second.

**Daily ticket sales**

5,000 tickets per day.

For planning purposes, this represents relatively moderate traffic. The system can distribute requests across several application servers and use caching for frequently accessed event information.

### 2.2 Popular Concert Sale Traffic

Given:
- People attempting to buy tickets = 200,000.
- Available seats = 20,000.
- Sale window = 10 minutes = 600 seconds.

**Average purchase attempts per second**

200,000 ÷ 600 ≈ 333.33 purchase attempts per second.

**Average seats available for sale per second**

20,000 ÷ 600 ≈ 33.33 seats per second, if sales were evenly distributed.

**Demand-to-supply ratio**

200,000 ÷ 20,000 = 10.

There are approximately 10 interested buyers for every available seat.

The system must therefore handle much higher traffic during this sale than on a normal day.

### 2.3 Comparison and Planning

| Metric | Normal day | Popular concert sale |
|---|---:|---:|
| Visitors or purchase attempts | 50,000 visitors | 200,000 attempts |
| Time period | 24 hours | 10 minutes |
| Page views | 500,000/day | Not specified |
| Average page views per second | 5.79 | Not provided |
| Ticket demand | 5,000/day | 20,000 seats |
| Average purchase attempts per second | Not specified | 333.33 |

The popular sale produces approximately 333 purchase attempts per second during its 10-minute window. This is a concentrated workload and cannot be treated like normal daily traffic.

The 333 attempts per second is an average across the sale window. Actual traffic may arrive in much larger bursts, so the system should be designed with additional capacity and a waiting-room mechanism.

The waiting room controls how many users can enter the purchasing process at a time. This protects the application servers and database from being overwhelmed.

## 3. API Design

TicketHub will expose a REST API. JSON will be used for request and response bodies.

Base URL:

`https://api.tickethub.example/v1`

| Method | Endpoint | Description | Success status |
|---|---|---|---|
| GET | `/events` | Browse and search upcoming events | 200 OK |
| GET | `/events/{eventId}` | Retrieve event details | 200 OK |
| GET | `/events/{eventId}/seats` | View seats and their availability | 200 OK |
| POST | `/events/{eventId}/holds` | Temporarily reserve available seats | 201 Created |
| POST | `/orders/{orderId}/pay` | Initiate payment for an order | 202 Accepted |
| GET | `/users/me/orders` | View the authenticated user's orders | 200 OK |
| GET | `/users/me/tickets` | View the authenticated user's tickets | 200 OK |

### 3.1 Browse Events

Request:

`GET /events?location=Nairobi&category=concert`

Example response:

```json
{
  "events": [
    {
      "id": 101,
      "name": "Summer Music Festival",
      "location": "Nairobi",
      "date": "2026-12-20T18:00:00Z",
      "startingPrice": 2000
    }
  ]
}
```

### 3.2 View Available Seats

Request:

`GET /events/101/seats`

Example response:

```json
{
  "eventId": 101,
  "seats": [
    {
      "id": 501,
      "seatNumber": "A1",
      "status": "AVAILABLE",
      "price": 2000
    },
    {
      "id": 502,
      "seatNumber": "A2",
      "status": "HELD",
      "price": 2000
    }
  ]
}
```

Seat availability shown to users is informative. The database must verify availability again when a user attempts to hold a seat.

### 3.3 Hold Seats

Request:

`POST /events/101/holds`

Example request body:

```json
{
  "seatIds": [501, 502]
}
```

Example successful response:

```json
{
  "orderId": 9001,
  "status": "PENDING_PAYMENT",
  "heldSeats": [501, 502],
  "expiresAt": "2026-12-20T17:15:00Z"
}
```

The server creates a temporary hold, for example for 10 minutes. The user must complete payment before the hold expires.

If a requested seat has already been sold or held by another user, the server must reject that seat rather than create a duplicate reservation.

### 3.4 Pay for an Order

Request:

`POST /orders/9001/pay`

The request includes a payment method and an idempotency key to prevent duplicate payment processing when a client retries.

Example request body:

```json
{
  "paymentMethod": "CARD",
  "idempotencyKey": "payment-9001-attempt-1"
}
```

Example response:

```json
{
  "orderId": 9001,
  "paymentStatus": "PROCESSING",
  "message": "Payment is being processed."
}
```

The payment provider sends a confirmation through a verified webhook. Only after successful confirmation should the order be marked as paid and the tickets issued.

### 3.5 View Orders and Tickets

`GET /users/me/orders` returns the authenticated user's order history.

`GET /users/me/tickets` returns tickets belonging to the authenticated user.

The API must verify the user's identity and authorization before returning private order or ticket information.

## 4. Data Model

TicketHub will use PostgreSQL because ticket purchases require reliable transactions, relationships, and database constraints.

The main tables are:

1. `users`
2. `events`
3. `seats`
4. `orders`
5. `order_items`

The additional `order_items` table connects orders to the individual seats purchased.

### 4.1 Table Relationships

- One user can create many orders: one-to-many.
- One event can have many seats: one-to-many.
- One event can have many orders: one-to-many.
- One order can contain multiple seats through `order_items`: one-to-many.
- A seat can appear in an order item, but it must have no more than one active hold or completed sale at a time.

### 4.2 Database Schema

```sql
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    full_name VARCHAR(150) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash TEXT NOT NULL,
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE events (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(200) NOT NULL,
    description TEXT,
    location VARCHAR(200) NOT NULL,
    event_date TIMESTAMP NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'UPCOMING'
);

CREATE TABLE seats (
    id BIGSERIAL PRIMARY KEY,
    event_id BIGINT NOT NULL REFERENCES events(id),
    seat_number VARCHAR(30) NOT NULL,
    price DECIMAL(10, 2) NOT NULL CHECK (price >= 0),
    status VARCHAR(20) NOT NULL DEFAULT 'AVAILABLE',
    hold_expires_at TIMESTAMP,
    UNIQUE (event_id, seat_number),
    CHECK (status IN ('AVAILABLE', 'HELD', 'SOLD'))
);

CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(id),
    status VARCHAR(30) NOT NULL DEFAULT 'PENDING_PAYMENT',
    total_amount DECIMAL(12, 2) NOT NULL CHECK (total_amount >= 0),
    created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    expires_at TIMESTAMP,
    payment_reference VARCHAR(150) UNIQUE
);

CREATE TABLE order_items (
    id BIGSERIAL PRIMARY KEY,
    order_id BIGINT NOT NULL REFERENCES orders(id),
    seat_id BIGINT NOT NULL REFERENCES seats(id),
    status VARCHAR(20) NOT NULL,
    price_at_purchase DECIMAL(10, 2) NOT NULL,
    UNIQUE (seat_id),
    CHECK (status IN ('HELD', 'PAID', 'RELEASED'))
);

CREATE UNIQUE INDEX idx_order_items_active_seat
ON order_items(seat_id)
WHERE status IN ('HELD', 'PAID');

The unique constraint on `order_items.seat_id` ensures that a seat cannot be assigned to multiple order-item records. When a hold expires or an order is cancelled, its order item must be changed to `RELEASED`, allowing the seat to be assigned again.

### 4.3 Useful Indexes

```sql
CREATE INDEX idx_events_date
ON events(event_date);

CREATE INDEX idx_seats_event_status
ON seats(event_id, status);

CREATE INDEX idx_orders_user
ON orders(user_id);
```

These indexes help the system retrieve upcoming events, find available seats for an event, and retrieve a user's orders efficiently.

## 5. Preventing Double-Booking

Preventing two people from buying the same seat is one of the most important requirements of TicketHub.

For example, imagine users John and Mary both select seat A1 at almost exactly the same time.

If the application only checks whether A1 is available before creating an order, both users might see it as available and attempt to purchase it. This creates a race condition.

TicketHub must therefore enforce seat availability at the database level, not only in the frontend.

### 5.1 Database Transactions and Row-Level Locking

When a user requests a seat hold, the application starts a database transaction.

A simplified process is:

1. Start a database transaction.
2. Lock the requested seat rows using `SELECT ... FOR UPDATE`.
3. Check that the requested seats are available or have expired holds.
4. Update the seats to `HELD` and set a hold expiration time.
5. Create the order and its order-item records.
6. Commit the transaction.

Example SQL:

```sql
BEGIN;

SELECT id, status, hold_expires_at
FROM seats
WHERE id = 501
FOR UPDATE;

-- The application verifies that the seat is available
-- or that its previous hold has expired.

UPDATE seats
SET status = 'HELD',
    hold_expires_at = CURRENT_TIMESTAMP + INTERVAL '10 minutes'
WHERE id = 501
  AND (
      status = 'AVAILABLE'
      OR (
          status = 'HELD'
          AND hold_expires_at < CURRENT_TIMESTAMP
      )
  );

-- The application must verify that exactly one row
-- was updated before creating the order.

COMMIT;
```

The application should create the order and order item within the same transaction. If any step fails, it should roll back the transaction.

### 5.2 Why This Prevents Double-Booking

When John locks seat A1, Mary's transaction must wait until John's transaction finishes.

If John successfully holds the seat, Mary's transaction will then discover that the seat is already held and reject her request.

The database's row-level lock prevents both transactions from successfully changing the same seat at the same time.

The unique constraint on `order_items.seat_id` provides an additional database-level safeguard against assigning the same seat to multiple orders.

### 5.3 Hold Expiration

A seat hold is temporary.

If a user does not complete payment within the hold period:

1. A background worker identifies expired holds.
2. The associated order is marked as expired.
3. The order item is marked `RELEASED`.
4. The seat is changed back to `AVAILABLE`.
5. The seat can be held by another customer.

The release process must also use a transaction and verify that the hold is still expired before changing the seat's status.

### 5.4 Payment Safety

Payment should happen outside the database transaction used to create the hold. External payment processing can take time, and keeping database locks open while waiting for a payment provider would reduce performance.

Instead:

1. The user creates a seat hold.
2. The system creates a pending order.
3. The user initiates payment.
4. The payment provider processes the transaction.
5. A verified payment webhook confirms success.
6. The system marks the order and order items as paid and the seats as sold, using a database transaction.

If payment fails or the hold expires, the system releases the seats according to its payment and expiration rules.

An idempotency key prevents repeated payment requests from creating duplicate charges.

## 6. System Architecture

### 6.1 Architecture Diagram

```text
                    USERS
                      |
              [ Web / Mobile Client ]
                      |
                     DNS
                      |
                     CDN
             (Static files and assets)
                      |
               [ Load Balancer ]
                      |
              [ Waiting Room / Queue ]
                      |
             [ API Gateway / Rate Limit ]
                      |
          +-----------+-----------+
          |                       |
   [ Application 1 ]       [ Application 2 ]
          |                       |
          +-----------+-----------+
                      |
              [ Cache Layer ]
          (Event details and listings)
                      |
              [ Primary Database ]
                 PostgreSQL
                      |
                [ Read Replica ]
                      |
          +-----------+-----------+
          |                       |
   [ Message Queue ]        [ Payment Provider ]
          |
   [ Background Workers ]
          |
   (Expire holds, send
    notifications, reconcile)
```

### 6.2 Component Explanations

**Web and Mobile Client**

Provides the interface for browsing events, viewing seats, purchasing tickets, and accessing digital tickets.

**DNS**

Translates the TicketHub domain name into the appropriate network address so users can reach the service.

**Content Delivery Network (CDN)**

Delivers static assets such as images, CSS, and JavaScript from locations closer to users. This reduces the load on the main application servers.

**Load Balancer**

Distributes incoming requests across healthy application servers, preventing one server from receiving all the traffic.

**Waiting Room and Queue**

Controls how many users can enter the purchasing process during a popular sale. It prevents 200,000 users from simultaneously overwhelming the application and database.

The waiting room should use a fair admission policy, such as first-in-first-out ordering after a clearly defined sale opening time. It should also use short-lived, signed queue tokens to prevent users from bypassing the queue.

**API Gateway and Rate Limiting**

Provides a central entry point for API requests. It can enforce authentication, request limits, and other security policies.

**Application Servers**

Handle business logic, validate requests, authenticate users, manage seat holds, and communicate with the database and payment provider.

At least two application servers provide redundancy if one becomes unavailable.

**Cache Layer**

Stores frequently requested event information and other suitable read data. This reduces repeated database queries.

Seat availability must be verified against authoritative database records before a hold or purchase is accepted.

**Primary Database**

Stores users, events, seats, orders, and order items. It is the authoritative source for seat ownership and purchase status.

**Read Replica**

Handles suitable read-heavy queries, reducing pressure on the primary database. Seat reservation and purchase decisions must still use the primary database to avoid relying on stale availability information.

**Message Queue**

Stores background tasks so that the main API does not have to wait for every secondary operation to finish.

**Background Workers**

Process tasks such as expiring seat holds, sending booking notifications, and reconciling payment results.

**Payment Provider**

Processes customer payments. It communicates payment results through verified callbacks or webhooks.

### 6.3 How the Architecture Handles a Popular Sale

During a popular concert sale, 200,000 people may attempt to purchase tickets within 10 minutes.

The waiting room controls admission rather than allowing every user to reach the purchasing API simultaneously.

The CDN serves static website assets, while the cache handles suitable event information requests.

The load balancer distributes admitted requests across application servers.

The primary database handles authoritative seat holds and purchases using transactions and row-level locks. The read replica supports suitable browsing queries.

Background workers release expired holds and process notifications without blocking the main API.

Monitoring tracks queue length, API response times, database connections, failed requests, and payment status.

The system can also scale application servers horizontally as demand increases. However, database capacity and the rate at which seats can be safely reserved must also be considered.

## 7. Architectural Trade-Offs

### Trade-Off 1: Waiting Room vs. Immediate Access

**Advantages:**
- Protects application servers and the database from sudden traffic spikes.
- Gives the system control over how many users enter the purchasing process.
- Can provide a fair admission process.

**Disadvantages:**
- Users may have to wait before purchasing.
- Queue infrastructure introduces additional complexity.
- Poor queue design could create unfairness or allow automated bypassing.

**Decision:** Use a virtual waiting room for high-demand sales while allowing normal browsing without unnecessary delays.

### Trade-Off 2: Strong Database Consistency vs. Performance

**Advantages of strong consistency:**
- Prevents two customers from successfully reserving the same seat.
- Maintains accurate order and seat ownership records.

**Disadvantages:**
- Row-level locks and transactions can reduce throughput when many users compete for the same seats.
- Database contention can increase response times.

**Decision:** Use transactions and row-level locking for seat reservations and purchases. Use caching and read replicas for suitable browsing operations, where slightly stale information is acceptable.

Correctness is more important than displaying an immediately updated seat map.

### Trade-Off 3: Temporary Holds vs. Direct Purchase

**Advantages of temporary holds:**
- Gives customers time to complete payment.
- Prevents other users from taking a seat during checkout.

**Disadvantages:**
- Some users may hold seats without completing payment.
- Seats can remain unavailable until their holds expire.

**Decision:** Use short-lived holds with automatic expiration and background cleanup.

## 8. Conclusion

TicketHub must support normal event browsing while remaining reliable during sudden, high-demand ticket sales.

The most important design decision is to protect seat ownership through database transactions, row-level locking, and uniqueness constraints. A virtual waiting room controls traffic, while caching, load balancing, multiple application servers, and background workers improve scalability and reliability.

The design balances speed, fairness, correctness, and availability. No matter how many people attempt to purchase the same seat, the database must allow only one valid active reservation or completed sale.
